# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

**Dogfood 2026** — a self-hostable hackathon submission and judging platform, built as an entry to the "Dogfood 2026" hackathon (see `docs/EVENT_DESCRIPTION.txt` and `docs/spec.md`). The competition's own premise is recursive: contestants build the platform that will judge them, judged by an automated Python checker (`scripts/run.py`, provided by the organizers, not to be modified) against a `.dogfood.toml` file and shared `fixtures.json` data.

Submissions are scored against four tiers, each strictly gating the next (`docs/REQUIREMENTS.md` has full feature detail):
- **T1 Core** — auth, event lifecycle, teams, submissions, public gallery.
- **T2 Judging** — judge assignment, rubric scoring, backend-enforced role isolation, normalization, CSV export.
- **T3 Public** — community voting, anti-abuse, unbiased ordering, audit log.
- **T4 Stretch** — REST/OpenAPI, webhooks, Ed25519-signed results, certificates, embeds.

**Current implementation status (check before assuming a feature exists — this moves fast across branches):**
- Implemented on `feat/Tier-4-initial` (this branch, before merging `master`): offline auth, event-contextual RBAC, home/gallery/hackathons pages, judging-normalization math, and Tier 4's buildable slice — 4.1 Ed25519 signing, 4.2 embeddable gallery widget, 4.3 atomic export/import, 4.4 OpenAPI coverage + API tokens (see `docs/TIER4.md` for the full writeup, including documented deviations from the original spec and why 4.5/4.6/4.7 are deferred there).
- `master` has since grown a full team engine, event creation/admin dashboard, profile, and — importantly — **a real T2 judging engine** (`src/server/judging-service.ts`, judge/organizer routes, rubrics, assignments, pairwise rankings) that did not exist when `docs/TIER4.md`'s "defer 4.5/4.6/4.7" decision was made. That decision should be revisited once this branch is merged with `master`, since the T2 prerequisite it was blocked on may now be satisfied.
- Before assuming a feature exists or is missing, check the actual route/component and `git log` — don't trust a stale doc.

## Tech stack

- **Framework:** Next.js 15 (App Router, `app/`), React 19, TypeScript 5.6.
- **Styling:** Tailwind CSS v4 + shadcn/ui (`components.json`, style `base-nova`, aliases `@/components`, `@/lib`, `@/components/ui`). Icons: `lucide-react` only.
- **DB:** PostgreSQL via `drizzle-orm` (0.35, pinned — see migration note below) + `postgres` (postgres.js driver). Schema source of truth: `src/db/schema.ts`. Migrations: `drizzle/*.sql` + `drizzle/meta/_journal.json`.
- **Auth:** Argon2id password hashing (`argon2` package), opaque random session tokens (SHA-256 hashed at rest) in an `HttpOnly`/`SameSite=Lax` cookie (`dogfood_session`), or a `Bearer dfk_...` API token (`src/server/token-service.ts`) — both resolve through the same `requireSession()` in `src/server/http.ts`, so RBAC never needs to know which one was used.
- **Validation:** Zod schemas (`src/lib/api/schemas.ts`, `src/lib/api/export-schema.ts`) at every API boundary.
- **Object storage:** SeaweedFS (S3-compatible), configured via `docker-compose.yml`.
- **Signing:** Node's built-in `crypto` (Ed25519) — `src/server/crypto/keys.ts` (keypair lifecycle), `src/server/signing-service.ts` (sign/verify envelopes), `src/lib/canonical-json.ts` (deterministic serialization these signatures are computed over).
- **API docs:** `swagger-ui-react` at `/api/docs`, served from `GET /api/openapi.json`, generated by `src/server/openapi.ts`'s hand-rolled registry (not `@asteasolutions/zod-to-openapi` — a deliberate, documented deviation).
- **Runtime tooling:** `tsx` for running TS scripts directly, `vitest` for tests (plus `jsdom` for the one test file — `t4-embed-js.test.ts` — that executes `public/embed.js` as a real script), `pnpm@12.3.4` as the pinned package manager (`package.json`'s `packageManager` field — use pnpm, not npm/yarn, for local dev; the Dockerfile itself uses `npm ci`/`package-lock.json`, so both lockfiles must be kept in sync on every dependency change).
- **Package manager environment note:** `pnpm-workspace.yaml` has an `allowBuilds` map that pnpm 10+ requires set to `true`/`false` per native-postinstall package to approve non-interactively — new native deps will need an entry added here or `pnpm install` fails closed.

## Commands

Local dev (outside Docker) needs Postgres + SeaweedFS reachable per `.env.example`; copy it to `.env` first.

```bash
pnpm install                 # install deps (frozen-lockfile in CI/containers)
pnpm dev                     # next dev
pnpm build                   # next build
pnpm start                   # next start (production server)

pnpm db:generate              # drizzle-kit generate (new migration from schema.ts changes)
pnpm db:migrate               # tsx scripts/migrate.ts — runs drizzle-orm's own migrator directly,
                               #   NOT `drizzle-kit migrate`: drizzle-kit 0.28 requires
                               #   compatibilityVersion 10 but this repo pins drizzle-orm 0.35
                               #   (version 9), so drizzle-kit's migrate command always fails here.
                               #   In practice, migrations in this repo are hand-authored SQL matching
                               #   drizzle/0000_t1_core_auth.sql's style — tests/acceptance/schema.test.ts
                               #   fails if a Drizzle column has no matching line in drizzle/*.sql.
pnpm db:seed                  # tsx scripts/seed.ts — creates the fixed dev users (see below)
pnpm db:fixtures              # tsx scripts/load-fixtures.ts — loads src/db/fixtures.json (idempotent)
pnpm seed                     # alias of db:seed

pnpm test                     # vitest run — all tests under tests/acceptance/*.test.ts
npx vitest run tests/acceptance/auth.test.ts   # run a single test file
npx vitest run -t "some test name"             # run tests matching a name

pnpm cli -- <command> --flag=value   # scripts/cli.ts: create-user, list-users, export, backup, import
pnpm openapi                  # tsx scripts/generate-openapi.ts -> writes openapi-spec.json — re-run this
                               #   after adding/changing any route in src/server/openapi.ts's apiRoutes
pnpm verify -- --file=envelope.json --key=pub.pem   # scripts/verify.ts — standalone, no DB/network,
                               #   verifies a signed Ed25519 envelope (results manifest/export/etc)
pnpm acceptance                # vitest run && tsx scripts/run-acceptance.ts (the run-acceptance step is currently a stub)
```

Docker (the way the project is meant to be graded — see `docs/ARCHITECTURE.md`):

```bash
docker compose up                          # builds image, migrates, seeds, fixtures, prints test-login cookies
docker compose run --rm cli npm test       # run the vitest suite with zero host setup
```

Seeded dev accounts (`scripts/seed.ts`, password `DogfoodLocal1!` for all, or use `/api/auth/impersonate` when `NODE_ENV!=production` and `OFFLINE_MODE=true`): `admin@local` (SUPERADMIN), `organizer@local`, `judge1@local`, `participant@local`.

There is no lint script currently defined in `package.json`; `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` will not fail on type errors — run `npx tsc --noEmit` explicitly to check types. Some destructive/live-DB tests (export/import round trip, token ownership) are gated behind `ALLOW_DESTRUCTIVE_DB_TESTS=true` plus a `DATABASE_URL` whose database name matches `/test/i` — see `docs/TIER4.md` for the exact invocation; a plain `pnpm test` never touches Postgres for these.

## Architecture

### Layering

Strict separation, don't blur these:
- `app/api/**/route.ts` — HTTP controllers only. Parse+validate with `parseBody`/a Zod schema from `src/lib/api/schemas.ts` (or `src/lib/api/export-schema.ts`), call a `src/server/*-service.ts` function, map the result with `src/server/http.ts` helpers, catch errors through `authErrorResponse`. No business logic here.
- `src/server/*-service.ts` — business logic + Drizzle queries. This is the only layer allowed to touch `src/db`, with one exception: `src/server/crypto/keys.ts` is the *only* module allowed to touch the `signing_keys` table or the private-key PEM file — `signing-service.ts` goes through it (`findSigningKeyRow`/`getSigningKeyPair`), never `src/db` directly, which is also what makes it mockable as one unit in tests.
- `src/db/schema.ts` — Drizzle table defs **and** the domain's pure functions/invariants (`deriveEventStatus`, `canEditSubmission`, `isPublicSubmission`, `validateTeamSize`, normalization math, etc.). Treat this file as the spec-compliance source of truth, not just table shapes.
- `src/lib/**` — pure, isomorphic helpers shared by server and client (formatting, gallery filtering/sorting, nav active-state, judging math, canonical JSON). No DB access.
- `lib/api-client.ts` — the **only** place browser components may call `fetch()` against this app's own API; components must go through the exported functions there rather than calling `fetch` directly.
- `components/` — one shared components directory (`ui/` = shadcn primitives, `auth/`, `home/` = feature groupings). Don't create a second components root.

### Auth & RBAC model (read `src/server/auth-service.ts`'s bottom comment block before touching auth)

- Two-level RBAC: `users.role` is a **global** flag (only `SUPERADMIN` is meaningful globally; bypasses all event checks). Every other permission is **event-scoped** via the `event_roles` table (`ORGANIZER`/`JUDGE`/`PARTICIPANT` per `event_id`), resolved through `resolveEffectiveRole`/`getEffectiveRole`. A user with global role `PARTICIPANT` can still be `ORGANIZER` of one event and `JUDGE` of another.
- Sessions are opaque random tokens, hashed (SHA-256) before storage in the `sessions` table; API tokens (`api_tokens` table, `dfk_` prefix) use the identical hash-then-lookup shape. Neither the raw session token nor the raw API token is ever stored — every request re-resolves identity server-side from the hash.
- `/api/auth/impersonate` only works when `isImpersonationEnabled()` (`NODE_ENV !== 'production' && OFFLINE_MODE === 'true'`) — it's a dev-only backdoor by design, not a bug.
- **The central failure mode the spec calls out explicitly** (`docs/spec.md`): hiding data in the UI is not access control — every judge-scoped, event-scoped, or ownership-scoped query must filter in the backend/DB query itself (see `gallery-service.ts`'s `isGalleryVisible` filtering pattern, or `token-service.ts#revokeToken`'s `(id AND userId)` WHERE clause, as templates), because the grading checker (`run.py`) and any real attacker hit routes directly and expect 401/403, not a friendly page.

### Event lifecycle state machine

`deriveEventStatus()` in `src/db/schema.ts` is the single source of truth for an event's *effective* phase (`DRAFT → REGISTRATION → SUBMISSION → JUDGING → PUBLIC_VOTING → ARCHIVED`), computed from timestamp columns against `now`, **not** trusted from the stored `status` enum column (which can go stale). Every service that gates on phase recomputes it from timestamps rather than reading `events.status` directly — follow this pattern for any new phase-gated feature.

### Signed envelopes (Ed25519, `docs/TIER4.md` 4.1)

Anything the platform publishes for offline verification (currently: arbitrary caller-supplied envelopes via `POST /api/verify`; eventually results manifests/judge records/certificates once T2/T3 fully land) uses one envelope format: `{ format: "dogfood-signed", version, type, alg: "Ed25519", kid, signed_at, payload, signature }`, where the signature covers every field except itself via `src/lib/canonical-json.ts`'s deterministic serialization. `GET /api/keys` publishes public keys (JWKS-like); the private key never leaves `src/server/crypto/keys.ts` or its PEM file (`SIGNING_KEY_PATH`, gitignored under `data/`).

### Export / import (`docs/TIER4.md` 4.3)

`src/server/export-service.ts`/`import-service.ts` move an event or the whole instance as one JSON envelope. Key invariants, easy to violate accidentally when touching either file:
- FK-safe order (`users`/`event_roles` first, `audit_logs`/`signing_keys` last) — both files iterate the same order.
- Every export query has an explicit `.orderBy(id)` so two exports of unchanged data are byte-identical.
- `password_hash`/token hashes/the private key are never exported; a user row missing `passwordHash` on import gets one shared per-import placeholder Argon2 hash (see `needsPlaceholderPassword`), and those user IDs are reported back so an operator knows to reset them.
- `audit_logs` is append-only on import (`ON CONFLICT DO NOTHING`); every other table upserts (`DO UPDATE`).
- "Is this instance empty" (`isEmptyGiven`) is **not** "zero rows anywhere" — `docker compose up` always seeds baseline users + the fixture event, so that check is precise: zero rows in teams/submissions/scores/votes/pairwise_comparisons, and every event's slug matches the known fixture slug. Get this wrong and `--force` becomes mandatory even for a fresh install.
- Every write path (`export.created`, `import.applied`, and — for tokens — `token.created`/`token.revoked`) writes an `audit_logs` row; this was a real gap once, don't reintroduce it on a new admin-grade action without a matching audit insert.

### Style guidelines (`docs/STYLE-GUIDELINES.md` — required reading before any UI work)

- Black-and-white first; green (`#16a34a`, dark-mode `#22c55e`) is the *only* accent — never use it for errors/warnings, never use gradients/glow.
- shadcn primitives first (`components/ui/`, `cn()` from `lib/utils.ts`) — don't hand-roll one-off buttons/inputs.
- Spacing is on a 4px scale with specific conventional values (see the doc for card padding, control heights, page-column widths) — don't invent ad-hoc pixel values.
- **Legacy exception:** some pre-existing pages/screens predate this guide and still use violet (`#635bdb`). Don't copy violet into *new* work; migrate to green opportunistically when touching those files. `components/site-header.tsx` is the reference implementation of the current guide.
- Every new screen must be checked in both light and dark mode.

### Grading/acceptance mechanics (important to not break)

- `scripts/run.py` is the organizers' checker — read-only reference, do not edit. It reads `.dogfood.toml` for `base_url`, per-role auth headers, and route paths, then makes plain HTTP requests expecting specific status codes.
- The single most heavily weighted check is that a judge can fetch their own scores (200) but a *different* judge's scores via the `peer_scores` route return 401/403 — this must be enforced at the query/service layer, not hidden client-side.
- `docker compose up` alone must produce a fully seeded, working portal with network access off (`OFFLINE_MODE=true`) — no cloud accounts, hosted DB, or external APIs. Don't introduce a dependency that needs outbound network access at runtime (this is also why `/api/docs`'s Swagger UI is bundled via `swagger-ui-react`, never loaded from a CDN, and why the embed CSP in `next.config.mjs` matters — array order there is load-bearing: the global `frame-ancestors 'self'` rule must be listed before the `/embed/:path*` override, since Next applies header rules in order and the last match wins).
- Required repo artifacts for submission: `.dogfood.toml`, an OSI-approved `LICENSE` file, a real `acceptance-report.txt` (check it isn't still the placeholder stub), and a demo video.
